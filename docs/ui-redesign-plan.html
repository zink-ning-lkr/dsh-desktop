00结论摘要

现有前端的工程质量明显高于同类 Electron 壳项目：令牌化设计系统、深浅双主题、单一事实源意识、63 条 A11y 声明、UITEST 像素契约、懒创建 + 60s 闲置回收的内存治理，都已具备。问题不在“做得糙”，而在三个结构性缺口——

① 没有壳层信息架构

桌面壳的 8 类自有能力（任务 / 更新 / 设置 / 报告 / 目录 / 快捷键 / 主题 / 关闭行为）全部压在 ☰ 菜单的单层 31 项列表里。主窗 30px 标题栏不承载任何状态，任务在跑、有更新可用、服务异常，都得去托盘看图标。

② 组件层只有 CSS，没有 JS

ui.css 把样式收成了单一事实源，但行为层仍在 9 个页面里各写一份——按钮行、进度条、结果视图、就地反馈各页重复实现，反馈时长都不一致（2600ms / 1800ms）。

③ 状态与反馈无全局宿主

没有应用级通知层：“已复制”“已保存”只能在按钮旁就地闪一下；“后台完成”只能靠系统通知。任务中心兼任 toast 宿主，但它只在有任务时才存在。

重构主张（一句话）

把 30px 标题栏升级为「命令栏」（高度不变，UITEST 契约不动），在其上挂载状态簇 + 命令入口； 新增命令面板（Ctrl+K）与应用内通知宿主； 把散落的 CSS 复用升级为真正的 JS 组件层（ui-kit.js，经典脚本 + window 命名空间，不引入框架与构建）； 并在阶段 0 先做一轮零行为变更的等价重构把地基理顺。

02短板诊断

按 结构层 → 实现层 → 体验层 三组排列，每项附仓库内可复查的证据。

结构层

S1壳层没有信息架构，单层菜单承担全部导航P0

桌面壳 8 类自有能力被拍平成一份列表：工作目录、重启服务、浏览器、全屏、标题栏、重新加载、DevTools、外观、关闭行为、下载加速、桌面更新、dsh 更新、快捷键、日志、内存、托盘状态……无分组层级、无搜索、无最近使用、无状态可见性。用户想“看看更新下载到哪了”必须先想起 ☰ → 任务中心。

menuItems() 单层数组 → main.js:1200-1270；菜单文案 31 条 i18n/zh-CN.json[menu]；菜单渲染器无分组/无搜索 menu.html:68-125

功能越多越难找，新增能力只能继续往菜单里塞；这是唯一一个会随版本恶化的结构性问题。

S2窗口模型碎片化：7 个独立小窗，4 个固定死尺寸P0

每项能力都有独立窗口、独立尺寸、独立入口，且绝大多数 resizable:false。在 125%/150% 系统缩放下，固定像素高（566 / 560 / 220）要么裁切要么大片留白。只有 report 窗做了 minWidth/minHeight 自适应，其余全靠内部滚动兜底。

固定尺寸且不可缩放：status main.js:530 410×186 ｜ dialog main.js:868 460×220 ｜ accel main.js:964 520×566 ｜ welcome main.js:1832 480×560
对照：report main.js:1105 760×600 min 640×480 resizable ✓

同一类窗口在不同 DPI 下体验不一致；长内容（accel 的 npm 指引、report 的建议列表）只能憋在滚动区里。

S3折叠标题栏的恢复交互不可发现P1

收起标题栏后，恢复入口是一个 96×26 的把手，只在鼠标进入窗口顶部中央 280×34 感应区（已浮现则 1.5× 迟滞）时才出现，靠 80ms 轮询驱动。这个机制本身写得很扎实（防闪烁、防空转），但没有任何视觉线索告诉用户“把手在这儿”——新用户收起标题栏后极可能以为窗口坏了。

HANDLE_ZONE 280×34 / HANDLE_W×H 96×26 / 80ms 轮询 main.js:198-249；把手页面 reveal-tab.html

首次收起标题栏 → 不知道如何恢复 → 误判为 Bug。（当前仅靠 README 文字说明覆盖）

实现层

C1组件层只有 CSS 复用，没有 JS 组件P0

ui.css 的注释自己记录了这段历史：按钮、结果圆标、窗口头部、就地反馈都曾“各页重复 2–4 份”，后来收编成公共类。但收编只到 CSS 为止——行为仍是各页一份：按钮行构造、进度条构造、结果视图渲染、反馈计时器，9 个页面各写一遍。改一次交互要动 N 个文件。

构造按钮行：status.html:169-180 与 dialog.html:71-80 与 report.html:125-131 三份同构代码
构造进度条：status.html:152-168（单视图与列表行共享，已是全仓最好的一处）
就地反馈：accel.html:152-158（2600ms） vs report.html:140-145（1800ms）——同一交互两个时长

一致性靠人肉维持，必然漂移；新增页面要重新踩一遍所有坑。

C2令牌层不完整：缺层级、缺状态、缺密度P1

颜色/字号/间距/圆角/时长这套已经很完整，但作为“设计系统”还缺三样：层级（elevation/z-index）、状态（hover/active/selected/disabled）、密度。另外圆角命名与取值脱节——--radius-s:6px 与 --radius-m:7px 只差 1px，视觉上不可辨，属于命名事故。

圆角：ui.css:80-82 --radius-s:6px; --radius-m:7px; --radius-l:10px
时长：ui.css:83-85 --dur-fast:.12s; --dur-mid:.15s（相差 30ms，无感知差异）
层级：全仓仅 ui.css:69 --c-elev-1 一处，无 z-index 表
状态：.btn ui.css:164-181 有 hover/active，无 :disabled（全仓无一处禁用态样式）

组件一旦需要禁用态/选中态/浮层叠序，只能现场硬编码，令牌体系从此出现例外。

C3任务中心 150ms 全量重渲染，无 keyed diffP1

进度帧每 150ms 到达一次，renderTasks() 每次都 list.innerHTML = '' 后整表重建。滚动位置、正在展开的历史折叠态、行内动画、鼠标悬停态都会被重置，同时高频触发整棵子树的样式重算与布局。当前靠 8 行以内的任务量掩盖了这个问题。

进度帧频率 main.js:355「进度帧(pushTasks)每 150ms 到达一次」
全量重建 status.html:281-317 list.innerHTML = '' + forEach(appendChild)

任务数上升到 10+ 或频繁增删时会可见抖动；这是唯一有真实性能上限的设计缺陷。

体验层

X1没有应用级通知宿主，轻量反馈无处安放P1

全仓唯一的“吸附式反馈”是 .inline-feedback——必须挨着触发它的按钮。于是状态类信息只能挤进两个不合适的地方：要么复用状态窗（而它只在有任务时存在），要么走系统托盘通知（打断性过强）。

就地反馈样式 ui.css:210-217；其消费者仅 accel 保存 / report 复制导出
状态窗兼任 toast：status.html:325-327 注释「瞬时 toast 永远渲染为列表中的一行」
主进程 notifyToast() main.js:611 直接走系统通知

“已切换外观”“已保存镜像源”这类零成本确认，目前在三种载体间摇摆，一致性由调用点决定。

X2主题跟随存在两条链路，可能不同色P2

自绘页走 ui-theme.js → matchMedia → 令牌覆写；而标题栏另走一套：采样 dsh 页面背景色后直接 body.style.background。两套并存意味着标题栏可能是“采样色”，而菜单/对话框是“令牌色”，在 dsh 页自定义主题或渐变背景时尤其容易露馅。

令牌链路 ui-theme.js:8-23；采样链路 titlebar.html:107-126 t.onTheme(({bg,fg,light}) => ...)
采样去抖 main.js:1464-1470（150ms）

视觉上出现“同一条窗口顶边两种颜色”的割裂；新增命令栏元素会立刻放大这个矛盾。

X3对话框声明了 modal 语义，但没有 modal 行为P0

决策对话框渲染层写着 role="dialog" aria-modal="true"，但窗口创建时只给了 parent（置顶）没有给 modal:true（输入阻断）。结果是：退出确认、破坏性操作确认弹出的同时，用户仍可继续点击主窗。这是无障碍声明与真实行为的直接矛盾，也带来“确认框挂着时误操作”的实际风险。

渲染层 dialog.html:35 role="dialog" aria-modal="true"
创建层 main.js:869 frame:false, resizable:false, skipTaskbar:true, show:false, parent: mainWindow —— 无 modal
全仓 grep modal: 零命中

读屏器告知用户“此对话框为模态”，用户却能把焦点移到背后的主窗继续操作——声明与事实不符，属正确性缺陷而非风格问题。

X4无障碍遗留四项P1
  • 列表行不可键盘操作：任务中心的 .trow 既无 tabindex 也无 roving 导航，行内 ✕ / 按钮只能靠 Tab 逐个穿行。
  • 交互承载在 <body> 上：下拉把手用 <body role="button" tabindex="0">，语义与可聚焦元素错位（reveal-tab.html:32）。
  • 无 landmark 结构：全部页面无 <main>/<nav>/<header> 角色，读屏器无法按区域跳转。
  • 快捷键不可程序化发现：菜单项的 accel 文本被 aria-hidden 并入 label，但未使用 aria-keyshortcuts（menu.html:117）。

这批基础做得越好，这四处越显眼；都是小改动、高收益。

X5i18n 有漏网，术语源分散P2

文案表已收编约 420 条，但仍有硬编码中文散在渲染层与共享模块里。对纯中文用户无感，一旦扩展到第二语言就会暴露。

硬编码「已启用」menu.html:115 accel.title = '已启用';
硬编码快捷键标签 shortcuts.js:7-12 label: '打开工作目录…'（未入 i18n 表）
自证注释 i18n.js:3-4「渲染层暂未接入（渐进收编）」

术语双源：菜单里同一动作的文案可能来自 i18n 表，也可能来自 shortcuts.js，改名时容易漏改。

03设计约束：9 条不可变项

以下每一条都来自现有代码事实或既有契约。方案中任何设计细节若与之冲突，以本节为准。

#约束依据与做法
1零框架、零构建不引入 React/Vue/Tailwind/打包器。组件层写成经典脚本 IIFE，挂 window.UI_KIT，与 ui-icons.js 同构。
2禁止 ES module页面经 loadFile() 运行在 file://，Chromium 视 module 为跨源请求并拒绝。全仓已确认无 module、无 protocol.handle 注册。若确需模块化，须先注册自定义协议——本方案选择不做，风险收益比不划算。
3CSP 不放松保持现有 CSP 原文。不新增 connect-src、不引外部字体/CDN。图标一律内联 SVG 白名单。
4沙箱 + 最小 IPC 面每个新窗口配独立 preload，只 contextBridge 暴露必要方法；主进程 handler 首行必 if (!trustedEvent(e)) return;。通道名沿用 域:动作 风格。
5四个单一事实源不动摇ui.css=样式与令牌 ｜ i18n/zh-CN.json=文案 ｜ ui-icons.js=图标 ｜ shortcuts.js=快捷键。新增 commands.js 作为第五个源（命令注册表），但必须由上述源合成而非平行复制。
6主题必须令牌化任何新组件的颜色/阴影/边框都只能引用令牌。主题切换只能靠 [data-theme="light"] 覆写令牌达成，组件零改动。新元素不得混用“采样色 + 令牌色”。
7UITEST 像素契约栏高 30、status 186/250、菜单 264+24、dialog min 200 为回归断言值，重构期不得改动；如必须改，同一提交内同步更新 uitest.js 断言与注释。
8内存纪律新增浮层视图（命令面板 / 通知宿主）必须走懒创建 + 关闭即销毁；辅助窗沿用 AUX_IDLE_DESTROY_MS = 60_000 闲置回收。不得新增常驻渲染进程。
9降级路径完整Win11 材质（Acrylic/Mica）不可用时自动回落实色（现状做法）；prefers-reduced-motion 下所有新动画必须同时禁用；文案表缺失时回退 key。

04目标架构

核心思路：不新增顶层窗口，把壳层能力下沉到主窗内的三层挂载点；辅助窗保持独立（它们的“可挂后台 / 模态 / 取证”语义有真实价值），只做外壳与尺寸归一。

图 1　目标架构：主窗三层挂载点（命令栏常驻 / 菜单与命令面板懒创建 / 通知宿主懒创建）+ 辅助窗外壳归一

4.1 三处关键取舍

取舍选择理由
是否引入侧栏 Rail不引入（保留为 P3 可选配置项）dsh 页面自身大概率已有侧栏，壳层再插一条 48–220px 的 Rail 会与内容区争夺左侧视线，且需为每个 dsh 布局做适配。当前收益不足以承担这个耦合。用命令栏状态簇 + 命令面板拿到约 80% 的价值。
是否新增顶层窗口不新增命令面板与通知宿主都作为主窗内的 WebContentsView 存在，复用已有的懒创建/销毁模式，不增加常驻渲染进程数（约束 8）。
辅助窗是否合窗保持独立，只归并外壳与尺寸策略任务中心需要 skipTaskbar:false 可挂后台、对话框需要模态、报告窗需要大尺寸取证、首启需要在主窗前独立出现——这些语义合并后都会丢。合窗的收益是“少几个窗口”，代价是四类语义全部退化。

main.js扩写paletteView / toastView 懒创建与销毁、notify() 统一出口、modal:true、settings.html 深链、状态簇推送否（不新增顶层窗口）
package.json扩写build.files 加入全部新文件否
uitest.js扩写新增用例：命令面板开合、toast 出现/自动消失、模态阻断、列表 keyed diff 后滚动位置保持、打包产物含新文件本文件即断言源

9.2 风险与对策

风险等级对策
命令栏增宽后挤压工作目录中按 §7.2 三级断点降级；工作目录保持 flex + max-width 截断；960px 最小宽下实测三态截图
新增两个视图造成内存上升中严格懒创建 + 关闭即销毁（对齐 menuPopupView / revealTabView 的现有模式）；在 SMOKE 用例里断言关闭后 webContents.isDestroyed()
toast 窗口抢焦点或挡点击中focusable:false + setIgnoreMouseEvents(true,{forward:true})；仅“带动作按钮的条目”在 hover 时临时开启鼠标事件（setIgnoreMouseEvents(false)），移出即恢复

组件层抽取引入回归高阶段 0 用“逐页面等价替换 + 每步跑 UITEST”的方式推进，一次只改一个页面；保留原函数名作为薄封装以便二分定位
误用 ES module 导致打包后白屏中列入 §10 自检项；ui-kit.js 采用 IIFE + window.UI_KIT，并在文件头注释写明原因（与 ui-icons.js 一致）

10验收自检清单

每个阶段合并前逐条对照。前 6 条是硬契约，后 6 条是质量门槛。

硬契约（违反即打回）

ui.css 中不出现页面级硬编码颜色；新增组件全部引用令牌
无 <script type="module">、无 import、无外部 URL 资源
UITEST 全绿：栏高 30 / status 186·250 / menu 264+24 / dialog min 200
新增文件已逐条加入 build.files，且安装包内实测存在
每个新窗口都有独立 preload；每个新 IPC handler 首行 trustedEvent(e)
无新增长驻渲染进程；浮层视图关闭后 webContents.isDestroyed() 为真

质量门槛

深浅主题切换后新组件零改动自适应；命令栏无“采样色 / 令牌色”混色
prefers-reduced-motion 下所有新动画禁用
键盘可达：面板全流程可纯键盘完成，焦点可见且关闭后归还 dshView
toast 不抢焦点、不挡点击（长按鼠标划过 toast 区域，下方内容仍可交互）
渲染层无硬编码中文；新增文案已入 zh-CN.json 并在表缺失时回退 key
125% / 150% 系统缩放下无裁切、无横向滚动条出现

一句话总结

这套前端的问题从来不是“做得糙”，而是九个页面各自长成了一套小系统——样式收成了一份，行为没收。 因此本方案把 70% 的工程量放在阶段 0 的零行为变更重构上：先把 ui-kit.js 这根轴承装进去，再谈命令栏、命令面板与通知宿主。 这样每一个后续阶段都只是“在新地基上摆家具”，而不是“边住边改承重墙”。
